# Python Port — Implementation Reference

Cross-cutting decisions, conventions, and context for the `ruby/` → `python/` port of Boukensha, gathered across steps 00–04. Read this before writing a new step's plan or reviewing an implementer's work — it exists so decisions made once don't need re-litigating (or silently drifting) every step. Per-step specifics live in `docs/plans/python_port/<NN>_<name>`; this file only holds things that apply *across* steps.

## Project Structure

- **One evolving package, not per-step duplication.** Ruby ships a fresh, fully self-contained `ruby/<NN>_<name>/` gem per step. Python is the opposite: a single project at `week1_baseline/python/` (`pyproject.toml`, one `src/boukensha/` package, one `.venv`), growing across steps via git history. The numbered folders (`python/00_config/`, `python/01_struct_skeleton/`, ...) hold **only** that step's runnable example + step-specific `README.md` — never a copy of the package itself.
- **`bin/` is gitignored repo-wide** (`.gitignore:13: bin/`), consistent for both `bin/ruby/*` and `bin/python/*`. Every step's entrypoint script (`bin/python/<NN>_<name>`) is created on disk and used for parity checks, but is **never committed** — only the step's `README.md` gets committed in that task. Commit messages for that task note this explicitly (see step 01/02's "add bin/python/NN entrypoint and step README" commits) so a future reader doesn't wonder where the script went.
- **Python version:** 3.13.3 via `pyenv` (pinned with `pyenv local` inside `python/`), chosen because pyenv-win's index had no stable 3.14 at decision time — revisit if that changes.
- **Dependencies stay minimal and stdlib-first**, matching Ruby's `ITERATIONS.md` philosophy: `PyYAML` + `python-dotenv` only, added in step 00. No new third-party deps introduced in steps 01–04 — step 03's backends are pure dict/list builders, and step 04's real HTTP client deliberately uses `urllib.request` (stdlib) rather than `requests`/`httpx`, mirroring Ruby's own explicit "no gems for HTTP" stance.
- **No pytest suite.** Every step ships no test suite in Ruby either — parity is verified by running `examples/example.py` and diffing its stdout against `examples/example.rb`'s, byte for byte **where the output is deterministic**. Step 04 is the first exception: it makes a real network call, so its response body is verified structurally instead (see that step's plan). Smoke checks inside each task are throwaway `python -c "..."` snippets, not persisted tests — except step 04's `Client` retry logic, which gets a mocked smoke check since the live parity check can't exercise the retry/failure branches on a healthy network. Don't add a test framework unless a future step's Ruby source actually adds one.

## Ruby → Python Idiom Mapping

These are the standing translation rules. Apply them by default; only deviate with a documented reason in that step's plan.

| Ruby | Python | Notes |
|---|---|---|
| Symbols as string-ish keys/values (`:player`, `:tokens`) | Plain strings (`"player"`, `"tokens"`) | Decided step 00: "plain-string API." No Ruby symbol/string duality to bridge — e.g. `Registry#dispatch`'s `args.transform_keys(&:to_sym)` has no Python equivalent and is simply dropped, not translated. |
| `attr_reader :x` (plain field) | Plain public instance attribute (`self.x = ...`) | E.g. `Config.dir`, `Config.settings`, `Context.task`, `Backend.model`. No property wrapper needed — Ruby's `attr_reader` is just exposing state, not computing it. |
| Zero-arg method with actual logic (`def mud_host; ...; end`) | `@property` | E.g. `Config.mud_host`, `Context.tool_count`, `Backend.context_window`, `Backend.headers`/`url`. Rule of thumb: if the Ruby method *computes* something from state (dict lookup, string formatting, default fallback), it's a property; if it just returns an ivar, it's a plain attribute. |
| Zero-arg method that transforms/converts (`to_s`, `to_messages`, `to_tools`) | Regular callable method, **not** a property | `to_*`-prefixed methods stay callable even at zero args, matching Ruby's own `to_s`/`to_i` convention of never being "just a field." `PromptBuilder.to_messages()`/`.to_tools()`/`.to_api_payload()` are plain methods for this reason, while `.headers`/`.url` (pure passthrough, no verb prefix) are properties. |
| `method_name?` (query method) | `method_name` (drop the `?`) | E.g. `Tasks::Base.prompt_override?` → `prompt_override`. Python identifiers can't contain `?`. |
| `method_name!` (bang/dangerous method) | `method_name` (drop the `!`) | E.g. `Backends::Base.validate_model!` → `validate_model`. No Python convention distinguishes "mutates/raises" via naming the way Ruby's bang does; don't invent one — just drop it. |
| `to_s` / `inspect` | `__repr__`, with `__str__ = __repr__` | Established step 00 (`Config`), reused every step since (`Context`, `Message`, `Tool`). |
| Implicit trailing block (`registry.tool(...) do |x| ... end`) | Explicit keyword argument | No Python syntax equivalent. Named `block=` (not `handler=`/`fn=`) to keep 1:1 traceability back to the Ruby source — decided in step 02. |
| A Ruby class method and instance method sharing one name (separate namespaces in Ruby, illegal collision in Python) | Rename one of them | Ruby's `Backends::Base` has both `self.model_info(model)` (class-level lookup) and `model_info` (instance-level cached reader) — legal in Ruby (singleton-class vs instance-class method tables), impossible in Python (same class `__dict__` slot). Resolved in step 03 by renaming the class-level lookup to `model_info_for(cls, model)` and keeping the instance-level value as a plain attribute (`self.model_info`, per the `attr_reader` rule above). **Watch for this pattern in future steps** — anywhere Ruby has both `self.foo` and `foo` methods on the same class. |
| `StandardError` subclass | `Exception` subclass, `pass` body | `UnknownToolError`, `UnsupportedModelError`. No custom `__init__` unless Ruby's constructor does more than accept a message. |
| Ruby `nil` in a data table (e.g. `cost_per_million: { input: nil }`) | Python `None` | Straightforward; `json.dumps` renders `None` as `null`, matching `JSON.generate`'s `nil` → `null`. |
| `ArgumentError` (Ruby's generic bad-argument error) | `ValueError` | E.g. `Tasks::Base.provider`/`.model` (step 00), the provider-dispatch `else` branch in each step's `example.py` (step 03). No new Boukensha-specific exception type unless Ruby introduces one (`errors.rb`) for that exact case. |
| Ruby module nesting (`Boukensha::Backends::X` vs `Boukensha::X`) | Mirror the nesting, don't flatten everything | `Tool`/`Message`/`Context`/`Registry`/`Config`/`Player`/`PromptBuilder` are all directly under `Boukensha::` in Ruby and are flattened into the top-level `boukensha` package's `__init__.py`. `Backends::Anthropic` etc. live under a nested Ruby module and get their own `boukensha.backends` subpackage with its own `__init__.py`, imported as `from boukensha.backends import Anthropic`, not `from boukensha import Anthropic`. |
| `JSON.pretty_generate(hash)` | `json.dumps(dict, indent=2)` | Both preserve insertion order and use 2-space indents; verified byte-identical output empirically in step 03 rather than assumed. If a future step's payload ever mismatches, adjust `separators=`, don't hand-roll a serializer. |

## Known, Deliberately-Unfixed Warts

The Ruby tutorial source has a few acknowledged rough edges that later steps promise to fix "later" (per `ITERATIONS.md`) but haven't yet as of step 03. **Port these warts as-is — do not silently fix them in the Python port.** If a reviewer flags one as a defect, the answer is "tracked here as an intentional carry-over," not a bug in the port.

1. **`Context` still owns `tools`, not `Registry`.** Introduced in step 02: `Registry#tool` still calls `context.register_tool(tool)`, and `Registry#dispatch` still reads from `context.tools`. `Registry` has no `tools` collection of its own. `ITERATIONS.md`: *"Context is still responsible for managing tools which is not correct... We'll correct this manually in a future step."* Not yet fixed as of step 03.
2. **`PromptBuilder.to_messages()` has an arity bug for stateful backends.** Introduced in step 03: it calls `backend.to_messages(context.messages)` with one argument. This matches Anthropic's and Gemini's `to_messages(messages)` (system sent as a separate top-level field) but **raises `TypeError`/Ruby's `ArgumentError`** for Ollama/OllamaCloud/OpenAI, whose `to_messages(system, messages)` requires two (system prompt gets folded into the messages array for those APIs). Not exercised by any `example.rb`/`example.py` — both only ever call `to_api_payload()`, which calls `backend.to_payload(context, ...)` directly and never routes through the broken `PromptBuilder.to_messages()` path.
3. **Python-only, step 05: `Message.__repr__`'s truncation doesn't `str()` non-string `content` first.** Ruby's `Message#to_s` does `content.to_s[0..60]` (stringify, then truncate); Python's `message.py` does `self.content[:61]` (truncate directly). Harmless while `content` was always a string (steps 00–04); step 05's `Agent._handle_tool_calls` is the first place a `Message` is ever constructed with list `content` (the raw normalized `content` blocks, stored on the `"assistant"` message). Nothing in step 05's code path calls `repr()`/`str()` on that message, so this is unexercised — not a Ruby wart being carried over, but a latent Python-only gap flagged for whichever future step first serializes/prints a `Message`. **Confirmed still unexercised as of step 06** — `Logger._serialize_message` accesses `msg.role`/`msg.content` directly (building a plain dict), never calling `repr()`/`str()` on the `Message` object. Still flagged, still not fixed, for whichever future step actually triggers it.

## Ruby Source Drift (not Python gaps)

Because each `ruby/<NN>_<name>/` folder is an independent snapshot (not an accumulating diff), the tutorial author has occasionally **removed and later re-added** a feature across steps — usually to keep an early step focused, not on purpose as a design change. When you see the Python port "already having" something a Ruby step's diff claims to introduce, check whether this is what happened before assuming an error:

- **`Config::PROMPTS_DIR`** (and the `default_prompts_dir` plumbing in `Tasks::Base`): present in `ruby/00_config`, **absent** in `ruby/01_struct_skeleton` and `ruby/02_the_registry`, restored in `ruby/03_prompt_builder`. The Python port ported it once in step 00 and never removed it (there's no reason to, since Python doesn't duplicate per-step folders) — so `config.py`/`tasks/base.py` already matched step 03's target state two steps early. Confirmed by diffing `ruby/00_config/lib/boukensha/config.rb` against `ruby/01_struct_skeleton`'s copy.
- **`Config.mud_host`/`mud_port`/`mud_username`/`mud_password` and `errors.LoopError`**: present through `ruby/05_agent_loop`, **removed** in `ruby/06_the_logger` (confirmed unused, and the Python port removed both to match — see step 06's Tasks 1–2), **restored** in `ruby/07_the_run_dsl`, still unused by any code path. Unlike `PROMPTS_DIR`, the Python port actually deleted these in step 06 (matching Ruby's own deletion) and had to re-add them in step 07 (matching Ruby's own re-addition) — a real two-way round trip, not just a "ported once, never removed" case. Confirmed via grep against `ruby/07_the_run_dsl/lib` and `examples/` that neither is called anywhere.
- **General pattern:** before writing a "Reference Files" diff table for a new step, diff the *previous* Ruby step's file against the *new* one directly (`diff -u ruby/<prev>/lib/boukensha/x.rb ruby/<new>/lib/boukensha/x.rb`) rather than trusting that step's README — the README has repeatedly (steps 00–02, confirmed again in 03) shown either stale/illustrative example output or copy-paste artifacts (see next section).

## Testing & Verification Approach

- No automated test suite in either language for steps 00–05. Parity is: run `bin/ruby/<step>` and `bin/python/<step>`, diff stdout, expect empty diff — **except steps 04+**, whose response body is inherently non-deterministic (a real LLM reply), so parity there is structural (preamble diffed exactly, response checked for expected JSON keys/shape) rather than a blind full-output `diff`. See that step's "A Note on Non-Determinism and Live Calls." Step 05 raises the stakes further: it's not one call but a whole agent loop (2+ calls per run, tool-call content and iteration count vary run to run), so its structural check also verifies the assistant-before-tool_result ordering invariant held (proxied by tool-call/tool-result print lines appearing in matching pairs, since a real ordering violation surfaces as an uncaught `ApiError`, not a silent formatting glitch).
- Each plan's tasks include inline smoke-check snippets (`python -c "..."`) that are run once during implementation and then discarded — not committed as test files. Step 04's `Client` is the first case needing a *mocked* smoke check (via `unittest.mock.patch` on `urllib.request.urlopen`/`time.sleep`) rather than a live call, since its retry/backoff branches can't be exercised on a healthy network and the plan verifies the logic before committing to it, not just after.
- Every plan's final task is a **cross-language parity check** that also re-runs *all prior steps'* Python entrypoints as a regression check, since the package is shared and cumulative — a change in an early step's file could silently break a later step. **This isn't hypothetical — it happened in step 06.** Removing `Config.mud_host`/`mud_port`/`mud_username` (dead code by that point in `python/src/boukensha/`) broke `python/00_config/examples/example.py`, which still printed `config.mud_host`/`config.mud_port` in its demo output. A grep across `python/src/boukensha/` alone (the shared package) missed this, because the caller lived in a **step folder** (`python/<NN>_<name>/examples/`), not the package. **When removing anything from the shared package, grep `python/*/examples/` too, not just `python/src/boukensha/`** — the regression check's re-run of prior entrypoints is what actually catches this class of bug in practice; a source-level grep isn't sufficient on its own. Fixed by removing the two stale print lines from `00_config`'s `example.py` — its own "known good transcript" necessarily changed as a result, which is expected under this project's one-shared-package model, not a bug.
- When a plan's "Behavior to Preserve Exactly" section includes a transcript, that transcript must have been captured by actually executing the Ruby example in this environment during plan-writing, not copied from a README. **Exception:** steps that make real, billed network calls (step 04 onward) require confirming with the user before making that live call, since it has a real-world cost/side-effect prior steps didn't have.

## Platform Notes

- **Windows console encoding can silently break `print()` of non-ASCII characters, with no Ruby-side equivalent problem.** Discovered in step 05: `agent.rb`'s tool-call trace prints a `→` (U+2192), ported verbatim into `agent.py`. Ruby's `puts` handles this transparently in this environment; Python's `sys.stdout` on Windows defaults to the console's ANSI codepage (not UTF-8) whenever stdout isn't attached to an interactive terminal — which is exactly the case for every parity check (`bash bin/python/<step> > file`) and for background/piped runs generally — raising `UnicodeEncodeError` the moment such a character is printed. Fixed by calling `sys.stdout.reconfigure(encoding="utf-8")` at the top of the affected `examples/example.py` (script-level, not library-level — `agent.py` itself stays clean since Python's `sys.stdout` is a single process-wide object, so the script's reconfiguration covers prints from anywhere, including library code it calls). **Watch for this in any future step whose Ruby source `puts`/`print`s a non-ASCII character** (arrows, box-drawing, emoji, etc.) — add the same `reconfigure` call to that step's `example.py` if so; steps 00–04 never needed it since none of their output included non-ASCII characters.

Steps 00 and 01 were done this way from the start.
- **Takeaway for future steps:** default to asking, or defaulting to direct in-session execution matching 00/01/02's actual precedent, rather than assuming the subagent-driven flow is wanted just because the plan header mentions it as recommended. If explicitly asked to use full subagent-driven-development (as was tried at the start of step 02), that's fine too — just don't be surprised if the user shortcuts it once they see the overhead of per-task subagent review round-trips on a small, mechanical plan.

## Per-Step Decision Log

Quick index of step-specific decisions that were non-obvious enough to need a call — full detail lives in each step's plan file.

- **Step 00 (`00_config`):** one-project packaging (not per-step); plain-string `Config.tasks("player")` API; `ValueError`/`NotImplementedError` for missing settings / abstract `task_name()`; src-layout (`python/src/boukensha/...`).
- **Step 01 (`01_struct_skeleton`):** `Tool.__repr__` manually renders `params=[:direction]` (Ruby-symbol style) instead of Python's default `dict.keys()` rendering, to stay diff-compatible with Ruby's output — a deliberate cosmetic exception to "plain strings everywhere," scoped only to that one `__repr__`.
- **Step 02 (`02_the_registry`):** block callables passed as an explicit `block=` keyword (see mapping table above); `Registry` intentionally has no `tools` dict of its own (see Known Warts above).
- **Step 03 (`03_prompt_builder`):** `backends` kept as a nested subpackage, not flattened (see mapping table); `Backends::Base`'s `model_info` naming collision resolved via `model_info_for` classmethod + plain `model_info` instance attribute; `PromptBuilder.to_messages()` arity wart ported as-is (see Known Warts above); no new custom exception for provider-dispatch fallback (`ValueError`, matching step 00's precedent).
- **Step 04 (`04_api_client`):** first step to touch real networking — `urllib.request` (stdlib) chosen over `requests`/`httpx`, matching Ruby's explicit "no gems for HTTP" stance; Ruby's `TRANSIENT_ERRORS` exception list translated via a documented best-effort mapping (no 1:1 equivalent between Ruby's and Python's networking exception hierarchies — see that step's plan for the full table); Ruby's OpenSSL cert-path workaround doesn't port at all, since `urllib.request` verifies certs via the OS trust store by default on every platform; `Tasks::Base` gained a shared `_fetch(settings, key)` helper (guards against non-`dict` settings) to mirror a real robustness fix Ruby made in this step, not just cosmetic churn. Also the first step where the example makes a real, billed network call, so parity is verified structurally (preamble diffed exactly, response body checked for expected keys) rather than by a blind byte-for-byte `diff` — see that step's "A Note on Non-Determinism and Live Calls."
- **Step 05 (`05_agent_loop`):** added `Agent` (`agent.py`) — the core loop — plus a `parse_response`/inverse-conversion (`_assistant_parts`/`_assistant_message`) contract on every backend so `Agent` never inspects a raw provider response (see idiom mapping table's spirit extended: normalize at the boundary, not in the loop). `LoopError` added to `errors.py` but confirmed unused anywhere in this step (`grep`-verified) — ported as dead code per "port warts as-is," not wired to anything. `tools:` keyword threaded through `Client`/`PromptBuilder`/every backend's `to_payload` exists for exactly one caller: `Agent`'s tools-disabled wind-down call (`tools=[]`) when the iteration ceiling is hit. Plan was written *without* a live-captured transcript (human partner declined to spend API credit twice, at plan-writing and execution) — a deliberate, confirmed deviation from the usual "transcript must come from a run" rule, with explicit live-confirmation gates left in the plan for execution time instead; at execution, both Python and Ruby were run live and compared structurally (matching preamble, matching `[iteration N/25]` markers, matching tool-call/tool-result pairing, non-empty final response) — full parity, no issues found beyond the expected dict-formatting cosmetic difference (`{'path': '.'}` vs `{"path"=>"."}`). Execution surfaced one unplanned fix: see "Platform Notes" for the Windows stdout UTF-8 issue (`agent.rb`'s `→` character), resolved via `sys.stdout.reconfigure(encoding="utf-8")` in `example.py`. One new latent-but-unexercised Python-only gap documented, not fixed: `Message.__repr__`'s truncation not `str()`-ing non-string `content` first (see Known Warts #3) — flagged for step 06 (the Logger) to pick up if it turns out to matter there.
- **Step 06 (`06_the_logger`):** added `Logger` (`logger.py`) — structured JSONL event logging — and wired `Agent` to call it at every phase, removing all stdout `print()` tracing from the loop entirely (the `[iteration N/max]`/`tool call →`/`tool result →` lines from step 05 moved into the log file exclusively; confirmed via a live run that stdout now contains only the deterministic preamble and final response). Also removed two pieces of dead code Ruby itself dropped this step: `LoopError` (added unused in step 05, never used, now gone) and `Config.mud_host`/`mud_port`/`mud_username`/`mud_password` (unused properties). `Agent`'s `logger: Logger.new` Ruby default (re-evaluated per call) required the standard `logger=None` sentinel in Python, since a literal `Logger()` default expression would share one session file across every `Agent` instance. `Boukensha.quiet!`/`quiet?` collided once `!`/`?` suffixes were dropped — resolved as `quiet()`/`is_quiet()` (and `debug()`/`is_debug()`), same collision category as step 03's `model_info`/`model_info_for`. Unlike step 05, this plan's "Behavior to Preserve Exactly" **was** grounded in a real live-captured transcript (both stdout and the full JSONL session log) captured during plan-writing, with the user's confirmation. **Execution surfaced a real cross-step regression**, not just a smoke-check nit: removing `Config.mud_host`/`mud_port`/`mud_username` broke `python/00_config/examples/example.py`, which still referenced them in its demo output — the source-level grep during planning only covered `python/src/boukensha/`, not step-folder `examples/` scripts; the step 8 (regression re-run) task is what actually caught it. Fixed by removing the two stale print lines from `00_config`'s `example.py` (see "Testing & Verification Approach" for the generalized lesson). No new Ruby/Python behavioral gaps introduced — `Message.__repr__`'s truncation gap (Known Warts #3) was checked again and confirmed still unexercised (`Logger._serialize_message` never calls `repr()`/`str()` on a `Message`).
- **Step 07 (`07_the_run_dsl`):** added `RunDSL` (`run_dsl.py`) and `boukensha.run()` (`__init__.py`) — a single top-level entry point wiring `Context`/`Registry`/backend/`PromptBuilder`/`Client`/`Logger`/`Agent` from just `task=` and a `block=` callback. Ruby's `RunDSL.new(registry).instance_eval(&block)` (rebinding `self` inside the block) has no Python equivalent — the port passes the `RunDSL` instance to the block explicitly instead (`block(RunDSL(registry))`, caller writes `def register_tools(dsl): dsl.tool(...)`), a real, permanent shape difference between the two DSLs, not a naming cosmetic. Backend classes (`Anthropic`/`OpenAI`/`Gemini`/`Ollama`/`OllamaCloud`) are imported inside `run()`'s function body rather than at `__init__.py` module level, to avoid `boukensha.Anthropic` becoming an accidental working attribute (Ruby's module nesting prevents this natively; Python has no equivalent, so the import is scoped instead — see that step's plan Confirmed Decision 4). `Logger` gained `turn(n)`/`subscribe(block)`, both dead code this step (never called), ported faithfully anyway per the established "port real, working code even if currently unused" precedent (`Logger.close` in step 06, `quiet`/`loud`/`is_quiet` before that). **`Config.mud_*` and `LoopError` made a real round trip**: both were deleted by the Python port in step 06 (matching Ruby's own step-06 deletion) and are back in step 07, restored verbatim, because Ruby's own snapshot restored them too — see the new Ruby Source Drift entry above for the general pattern this confirms a second time (after `PROMPTS_DIR`). Plan was written *without* a live-captured transcript (human partner declined a second time, same as step 05) — "Behavior to Preserve Exactly" was reconstructed from reading `ruby/07_the_run_dsl`'s source directly instead. At execution, both Python and Ruby were run live and compared structurally: identical preambles (module-name casing aside — `Boukensha.run` vs `boukensha.run` in the title line, expected and language-appropriate), identical JSONL phase sequences and `session_start` snapshot fields (`task`/`provider`/`model`/`max_iterations`/`max_output_tokens`) between the two runs, non-empty final responses on both sides — full parity, no issues found. `ruby/07_the_run_dsl/README.md` had three drift issues (wrong step number in the title, two nonexistent parameters — `token_budget:`/`max_tokens:` — in its options table, and an options table backend list missing 3 of the 5 real backends) — all corrected in the Python README rather than copied.
